# 事故：2026-10-09 调仓日崩溃（`topk=None` 埋雷）

> 状态：已修复并提交（`09299f4`，未推送）。今日调仓未能执行，周一 10-12 自动补。

## 一、结论

**当日失败不是"同花顺关了"，是代码 bug。** 关同花顺只让**第 1 次尝试**失败；
**重试那次同花顺已连上、下单前对账也已通过**，随后崩在策略内部。

```
TypeError: '<' not supported between instances of 'int' and 'NoneType'
  File "strategies/builtin.py", line 154, in generate_weights
    eff_topk = max(1, min(eff_topk, n))
```

## 二、根因

2026-10-02 的 P1-3 把 CLI `--topk` 改成「未显式传入则 **None 透传**」，
让各策略类定义的默认值生效 —— 但 `None` 守卫**只加在 `pipeline.run_backtest`**：

```python
# pipeline.py（有守卫）
if topk is not None:
    kw.setdefault("topk", topk)
```

而 `daily_run.bat` 实际调用的是 `main.py simulate --ths`（不带 `--topk`），
走的是 **`DailyRunner`**，它没有这个守卫：

```python
# scheduler/runner.py（修复前 —— 无守卫）
self.strategy = create_strategy(strategy, **_filter_kwargs(
    strategy, topk=topk, rebalance_every=rebalance, trend_window=config.TREND_LIVE))
```

`None` 经 `_filter_kwargs`（只按参数名过滤，不丢 None）原样注入策略 →
`self.topk = None` → 调仓日 `max(1, min(None, n))` 抛 TypeError。

### 为什么潜伏了 5 个交易日

| 机制 | 后果 |
|---|---|
| 调仓**每 5 次成功运行**才发生（`_since % rebalance_every == 0`）| 只有调仓日才走到第 154 行 |
| **失败不推进计数器**（`strategy_since` 只在成功路径落库，2026-09-29 改的）| 一旦踩中，之后**每个交易日都算调仓日**，天天崩 |

实测时序：10-02 改动 → 10-06/07/08 均非调仓（10-08 日志明写"下次调仓还需 1 次运行"，exit=0）
→ **10-09 第 20 次 = 首个调仓日 → 崩**。`strategy_since` 至今仍是 19。

## 三、修复

| 文件 | 改动 |
|---|---|
| `scheduler/runner.py` | `topk is None` 时**不注入**（与 `pipeline.run_backtest` 同口径）|
| `strategies/base.py` | `Strategy(topk=None)` 当场 `raise ValueError` —— 快速失败，不再拖到 5 天后的调仓日 |
| `tools/selftest.py` | 新增回归项「topk=None 不得覆盖策略默认值」：静态守卫 + 构造成 + **行为级调仓日断言** + 快速失败断言 |

## 六、教训

1. **改「参数透传口径」必须枚举全部消费方**。只给一条路径加 None 守卫，
   另一条（尤其实盘那条）就是埋雷。
2. **低频分支的改动，交付前必须主动构造样本把它跑到**。调仓每 5 次才走一次，
   等它日常自爆要等一周，一爆就是连续爆。
3. **不要接受"现象描述"里的因果归因**。用户说"关了同花顺"，日志显示重试时
   同花顺已连上、对账已通过 —— 现象可信，因果要自己用日志验一遍。
