## 二、每个 BUG 的修复方案与理由

### BUG-1 成本口径（选方案 A：引擎默认改为万5）

**改**：`tools/backtest_stock.py::run()` 默认
`cost_buy=0.0003 → 0.0005`、`cost_sell=0.0013 → 0.0015`。

**理由**：
1. `cost_buy/cost_sell` 是 **keyword-only**，全库**没有任何调用方传过**（`grep -rn cost_buy tools/*.py | grep -v backtest_stock` 为空）→ 改默认值就是唯一、也是最简的修法；在 5 个调用点各传一次反而又是"多处实现"。
2. 改后 **round-trip = 0.0030 = `MODELED_ROUND`** → 事后调整式与引擎口径**第一次自洽**。
3. 与项目已做过的事一致：`config.TRADING_COST.commission_rate` 早就是 0.0005（ETF 线已修），
   只有这个引擎漏了 —— 属**修正笔误**，不是新口径选择。
4. 方案 B（把 `MODELED_ROUND` 改成 0.0026）等于**官方承认"名义万5、实按万3"**，
   与主人真实费率不符；方案 C（只加注）留一个已知自相矛盾。均不取。

**副作用**：所有「10 万真实」数字**下降** 0.10~0.33pp（更保守）。
方向明确、量级可算，不改变任何排序或结论方向。

### BUG-7 涨跌停（重写判据）

**改**：`tools/backtest_stock.py::build_features()` 末段重写。

| 子项 | 改法 |
|---|---|
| 分档 | 用**代码前缀 + 日期**：科创 688/689 → 20%；**创业板 30x 且 date ≥ 20200824 → 20%，之前 10%**；北交所 BJ → 30%；其余 10% |
| 判据 | `.round(2)` 绝对价 → **比例判据 + 半格容差**：`open/prev_close − 1 ≥ lim − 0.005/prev_real` |
| 容差来源 | 优先用真实价（`px_real / close` 换算 `prev_real`），缺失时退回指数价 |
| 日期 | 内部自行 `date.astype(str).str.replace("-","")` 归一化，**不依赖调用方**（原来 `--start 2019-01-02` 这种带横线的日期会让字符串比较失效） |

**理由**：涨停价是"真实价 × (1+lim) 四舍五入到分"，而本项目喂给引擎的是**总收益指数价**，
在其上 round 到分有一半概率偏高一格 → 实测漏判 40.6%。比例判据在非除权日与真实口径等价。

**未建模项（已知残留，写清不掩盖）**：**ST 的 5%** 未处理 —— 池子按 `universe.is_st` 剔除，
但那是**当前快照**（非 point-in-time），池内中途转 ST 的会漏。要做对需要 ST 的历史状态，
当前数据没有 → 记录为已知限制，不硬造一个错的。

### BUG-2 / BUG-3 / BUG-4（单点笔误，直接改）

- BUG-2：`NOMINAL_FEE = 0.0003 → 0.0005`（与 `sweep_scaling.py` 同一套成本模型对齐）
- BUG-3：`diag_dividend_into_mf.py` 补 `--adj-mode`（纯透传，默认仍 `correct`）
- BUG-4：`项目运行手册.md` `--topk → --topn`

### BUG-5 / BUG-6（文档命令，统一策略）

| 问题 | 统一改法 |
|---|---|
| 缺 `--adj-mode` | 一律**显式补 `--adj-mode correct`**（默认值也是它，但显式写清 → 不再"静默"） |
| 缺 `--out` | 补 `--out results/adj_correct_<原名>.csv` |
| 指向 legacy 同名产物 | `results/xxx` → `results/adj_correct_xxx`（加前缀，不改含义） |

**理由**：本项目最在意「可复现」与「数字能追到哪次运行」。默认输出名就是 legacy 证据路径，
跑一次新口径就把它覆盖掉 → A/B 对照永久消失。**加前缀是零成本的保险**。
（同时已把 legacy 原件备份到 `results/_legacy_backup_20260917/`。）

### BUG-8 候选不足时的资金处理（选定：文档对齐实现 + 实盘写明偏离）

**决定**：
- **回测口径 = 等权买满**（不动引擎，不动既有数字）
- **实盘 = 每只 5%、不足 20 只则余下留现金**，并**明写这是有意偏离回测的保守选择**

**理由**：改引擎会让所有数字作废（等价于第三轮回灌），而"留现金"更保守、适合实盘；
把两者**分开写清**比强行统一更诚实。关键是不能混着引用。

## 五、成本控制在万5以内的具体分配

**预算口径**：`佣金费率 ≤ 万5`。下面是引擎与调整式**统一后**的完整拆解。

| 项 | 费率 | 收取方向 | 依据 |
|---|---|---|---|
| 佣金 | **万5（0.0005）** ← 预算上限 | 买入 + 卖出**各一次** | 主人实际费率；`config.TRADING_COST.commission_rate` |
| 单笔最低佣金 | **5 元/笔** | 买入 + 卖出**各一次** | 券商规则；10 万 ÷ 20 只 = **5,000 元/笔** |
| 印花税 | **万10（0.001）** | **仅卖出** | 法定，ETF 免征、个股不免 |
| 滑点 | **单边万5（0.0005）** | 买入 + 卖出**各一次** | 双边万10；与 `PriceRelatedSlippage(0.001)` 对齐 |
| **round-trip 合计** | **0.0030（0.30%）** | — | = 买(0.0005+0.0005) + 卖(0.0015+0.0005) |

**预算使用情况**：

| 检查项 | 结果 |
|---|---|
| 佣金费率是否超万5 | ❌ **没有**，正好等于万5（用满预算，不超） |
| 其余费用是否被误算成佣金 | ❌ 没有，印花税与滑点**单独列项**，未混进佣金 |
| 引擎与 `MODELED_ROUND` 是否一致 | ✅ 0.0026 → **0.0030**，现已自洽 |

### ⚠️ 必须说清的一件事：「有效佣金率」会到万10，这不是超预算

10 万 ÷ 20 只 = **5,000 元/笔** → 按万5 应收 **2.5 元 < 最低 5 元** →
**实收按 5 元**，即**有效佣金率 = 5/5,000 = 万10**。
这是**最低佣金规则**的必然结果，**不是费率超预算**（费率仍是万5）。
项目早已为此单独建模（`comm = max(NOMINAL_FEE, MIN_COMMISSION / ticket)`），
并把它量化为「最低佣金惩罚」（定稿 **0.28pp/年**）。

**因此成本控制的真正抓手不是费率，而是"别把单笔做小"**：

| 持仓数 | 单笔金额（10 万） | 有效佣金率 | 最低佣金惩罚 |
|---|---|---|---|
| N=20（**定稿**） | 5,000 元 | 万10 | 0.28pp/年 |
| N=10 | 10,000 元 | **万5（正好触线）** | 0 |
| N=30 | 3,333 元 | 万15 | 0.47pp/年 |
| `hold=20` 月度 | 5,000 元 | 万10 | 0.60pp/年（换手翻倍） |

→ **定稿选 `N=20` + `hold=60`**（季度）正是"少下单 + 单笔别太小"的平衡点：
836 笔 → 788 笔，最低佣金惩罚 0.28pp，且 10% 税档最低。**成本分配无需调整。**
